# ERVENOW — خريطة التسجيل مقابل Checkout (تحليل فقط)

**التاريخ:** 2026-09-22  
**النوع:** تصور قبل التنفيذ — لم يُغيَّر كود Login أو Checkout أو الطلبات أو الدفع.

القاعدة المتفق عليها: مساران لا يختلطان.

1. **إنشاء عضوية من `/login`** → OTP → نوع العضوية → الفئة → بيانات خفيفة → إنشاء.  
2. **ضيف يتسوق** → تصفح وسلة بلا حساب → عند «تأكيد الطلب والدفع» فقط OTP → Customer تلقائي إن كان الرقم جديدًا.

---

## 1. فئات المطاعم الحالية

المصدر التشغيلي: `shared/restaurantCategories.js` + جدول `categories` (`type=restaurant`, `scope=store`) عبر `/api/categories`.  
تسجيل المتجر يقرأ القائمة المدمجة (قاعدة ثم القائمة الافتراضية إن نقص الصف).

**المعتمدة للتسجيل والعرض (ليست hard-coded جديدة):**

| slug | الاسم الحالي |
|---|---|
| kabsa_bukhari | مطاعم كبسة وبخاري |
| shawarma_grill | مطاعم شاورما ومشاوي |
| seafood | مطاعم سمك |
| burger | مطاعم برقر |
| broasted | مطاعم بروستد |
| pizza | مطاعم بيتزا |
| cafe | مقاهي |
| sweets | حلويات |
| home_producers | أسر منتجة |

قديمة للعرض فقط (لا تُعرض كخيار تسجيل جديد): بخاري ومندي، برقر وبروستد، كبسة، فطور ومخابز، حلويات وقهوة، عصائر ومشروبات.

**ملاحظة على أمثلتك:** لا يوجد slug اسمه «سعودي» أو «وجبات سريعة». الأقرب لسعودي = كبسة وبخاري + شاورما ومشاوي. الوجبات السريعة تتوزع على برقر / بروستد / بيتزا / شاورما.

في الخلفية: `stores.type = restaurant` و`stores.category = slug`. Role المستخدم = `store` (Merchant Portal). المستخدم يرى «مطعم».

## 2. فئات المتاجر الحالية

نوع النشاط (`stores.type`) من `apps/store/routes.js` — هذا ما يجب أن يراه من يختار «متجر»:

| type | الاسم |
|---|---|
| supermarket | سوبرماركت |
| minimarket | ميني ماركت |
| pharmacy | صيدلية |
| beauty_care | التجميل والعناية |
| flowers_gifts | ورود وهدايا |
| clothing | الملابس والأزياء |
| vegetables | محل خضار |
| butcher | ملحمة |
| fish | بيع الأسماك |
| sweets | حلويات (كمتجر) |
| home_business | أسرة منتجة |
| other | غيره |

**ليست فئات متجر للتسجيل:** أقسام منتجات السوبرماركت (خضار، لحوم، ألبان…) وأقسام الملابس الداخلية (نسائي، رجالي، عبايات…). هذه تُستكمل داخل بوابة التاجر بعد الإنشاء.

**غير موجودة اليوم كنوع متجر:** إلكترونيات · مستلزمات منزلية. لا تُخترع في التسجيل حتى تُضاف رسميًا في `STORE_TYPES` + صفحة المتاجر.

Role: `store` → `/merchant-preview`.

## 3. فئات الخدمات الحالية

حساب مزود الخدمة: `users.role = service` + `service_type`.  
المصدر: `shared/utils/serviceProviderTypes.js` وصفحة الخدمات `section-hub-services.js`.

| service_type | الاسم | بوابة |
|---|---|---|
| plumber | سباك | service |
| electrician | كهربائي | service |
| ac_technician | فني مكيفات | service |
| laundry_estates | غسيل فلل وعمائر / تنظيف | service |
| agricultural_engineer | مهندس زراعي / تشجير | service |
| car_polishing | تلميع المركبات | service |
| gas_cylinder_swap | تبديل أسطوانات غاز | service |
| gas_central_refill | تعبئة غاز مركزي | service |

أسماء طلبات قديمة تُطوى عند التسجيل: `cleaning` / `cleaning_villa` / `cleaning_building` → `laundry_estates`، و`nursery` → `agricultural_engineer`.

**غاز:** ظاهر للعميل تحت باب «توصيل ونقل» في الرئيسية، لكن الحساب = Service Provider وليس Transport Role.

## 4. أنواع التوصيل والنقل الحالية

لا يوجد `role=transport` في قاعدة المستخدمين. النقل = `role=service` + `service_type` ثم Portal `transport`.

| ما يراه العميل / الشريك | القيمة الحالية | الحساب الداخلي | البوابة |
|---|---|---|---|
| مندوب توصيل | `role=driver` (+ مركبة `car` أو `bike`) | Driver | `/driver-preview` |
| توصيل داخلي / طرود | `internal_delivery` | غالبًا service_type؛ البوابة تُحوَّل Driver إذا كان النوع هذا | `/driver-preview` |
| دباب / سيدان / ونيت (للطلب) | فئة مركبة على الطلب: motorcycle / sedan / pickup_truck | ليست Role | مطابقة مركبة |
| سطحة / نقل مركبات | `pickup_truck` | service | `/transport-preview` |
| نقل أثاث | `furniture_move` | service | `/transport-preview` |
| غاز (اكتشاف العميل) | صفحات توصيل غاز | service + gas_* | `/service-preview` |

**غير موجود كنوع تسجيل مستقل:** «توصيل بدباب» و«توصيل بسيارة» كـ Roles. الموجود: مندوب (`driver` + نوع مركبة) أو توصيل داخلي (`internal_delivery` + فئة مركبة على الطلب).

## 5. ربط البطاقات الخمس بالأدوار الحالية

بدون Roles DB جديدة:

| بطاقة المستخدم | بعد اختيار الفئة | Role / حقول | الوجهة بعد الاعتماد |
|---|---|---|---|
| 👤 عميل | لا فئة | `customer` active | `/` |
| 🍽️ مطعم | slug مطعم من `/api/categories` | `store` + `stores.type=restaurant` + `category` | `/merchant-preview` |
| 🛍️ متجر | `stores.type` من قائمة المتاجر أعلاه | `store` + type | `/merchant-preview` |
| 🛠️ خدمات | `service_type` من قائمة الخدمات (بدون سطحة/أثاث/مندوب) | `service` | `/service-preview` |
| 🚚 التوصيل والنقل | مندوب → `driver`؛ سطحة/أثاث → `service` + type؛ طرود → `internal_delivery` كما هو اليوم | لا `role=transport` | Driver أو Transport preview |

مطعم ومتجر يبقيان نفس Merchant Role. الفرق للمستخدم فقط في البطاقة ثم الفئة.

## 6. فئات لا تعرف أين تندرج (تحتاج قرارك)

| العنصر | لماذا ملتبس | اقتراح للعرض |
|---|---|---|
| غاز | خدمة في الحساب، وتوصيل في الرئيسية | بطاقة **خدمات** للتسجيل؛ الاكتشاف يبقى في التوصيل |
| حلويات | slug مطعم `sweets` ونوع متجر `sweets` | مطعم إن كان «حلويات» مطبخًا؛ متجر إن كان محل حلويات/مخبز بدون طاولات — أو إخفاء نوع المتجر `sweets` من تسجيل المتجر |
| أسر منتجة | `home_producers` مطعم و`home_business` متجر | مطعم إن كان طعامًا جاهزًا؛ متجر إن كان منتجات |
| بيع الأسماك `fish` | متجر vs مطاعم سمك `seafood` | متجر = بيع؛ مطعم = طبخ |
| تلميع السيارات | في كتالوج الخدمات وفي باب المنزلية | **خدمات** |
| إلكترونيات / مستلزمات منزلية | غير موجودة في STORE_TYPES | لا تظهر حتى تُضاف رسميًا |
| توصيل بدباب / بسيارة | فئة مركبة لا Role | تحت **مندوب توصيل** كسؤال مركبة، لا بطاقة خامسة منفصلة داخل النقل |
| `stores.type=services` | نوع متجر اسمه خدمات | لا يُعرض في بطاقة المتجر؛ التسجيل من بطاقة خدمات |

## 7. تعديلات `/login` المطلوبة لاحقًا (لم تُنفَّذ)

الوضع اليوم بعد OTP لرقم جديد: 4 أزرار (عميل / متجر / مندوب / مزود خدمة) ثم نماذج طويلة، والمتجر يذهب فورًا إلى `/register-store` الثقيل.

المطلوب لاحقًا:

1. خمس بطاقات فقط بعد OTP (إنشاء عضوية)، بدون كل الفئات دفعة واحدة.  
2. الخطوة التالية = فئات حية من المصادر أعلاه (مطاعم من API، متاجر من STORE_TYPES بدون restaurant/services، خدمات من SERVICE_PROVIDER بدون النقل، نقل = مندوب + سطحة + أثاث + طرود).  
3. بيانات خفيفة فقط (اسم، جوال موثّق، فئة، موقع/حي إن لزم). صور، بنك، ساعات، منتجات، وثائق → داخل البوابة بعد الموافقة.  
4. عدم فتح `/register-store` كبوابة تسجيل كاملة في هذه المرحلة؛ أقصى حدّه خطوة بيانات خفيفة أو تأجيله للبوابة.  
5. `mode=register` من `/login` فقط هو من يرى البطاقات الخمس.

## 8. تعديلات Checkout المطلوبة لاحقًا (لم تُنفَّذ)

الوضع اليوم:

- التصفح والسلة ممكنان بلا حساب.  
- «تأكيد الطلب» بدون توكن يحوّل إلى `/login?mode=register&role=customer&next=/checkout`.  
- بعد OTP، الرقم الجديد يدخل مسار **إنشاء العضوية** (`needs_registration` + اختيار النوع). هذا يخلط المسارين.  
- الطلب التنفيذي أصلًا يحتاج جلسة؛ القاعدة «لا جوال موثّق → لا طلب قابل للتنفيذ» موجودة في الاتجاه، لكن بوابة الدخول الحالية قد تعرض اختيار العضوية في سياق الشراء.

المطلوب لاحقًا (بدون تغيير دورة الطلب/الدفع الآن):

1. Checkout OTP بسياق `checkout` / `login_only` + إشارة «أنشئ عميلًا إن لم يوجد» — **بدون** شاشة أنواع العضوية.  
2. إن وُجد Customer: ربط المسودة وإكمال الدفع.  
3. إن كان الرقم جديدًا: إنشاء `customer` تلقائيًا من التوكن ثم العودة للسلة/Checkout.  
4. إن كان الرقم لحساب شريك (متجر/مندوب/خدمة): سياسة صريحة (إكمال كعميل مرتبط بنفس الجوال أو رسالة «هذا الرقم مسجّل كشريك»). لم تُحسم هنا.  
5. قبل OTP: Cart / Draft فقط. بعد OTP + دفع/تأكيد: Order تصل للتاجر/المندوب/المزود.

`PUBLIC_ORDERING` على الخادم الحي كان معطّلًا (pre-registration). مسار الضيف للشراء يحتاج هذا العلم عند التنفيذ؛ لا يُغيَّر الآن.

---

## خلاصة المسارين

```
/login إنشاء عضوية
  OTP → 5 بطاقات → فئة → بيانات خفيفة → حساب (عميل فوري / شريك pending)

ضيف من الرئيسية
  تصفح → سلة → تأكيد الطلب والدفع → OTP فقط
    موجود Customer → ربط الطلب
    رقم جديد → Customer تلقائي → الدفع
    لا بطاقات عضوية ولا فئات شريك
```

لا تنفيذ حتى تعتمد خريطة الفئات وقرار البنود الملتبسة (غاز، حلويات، أسر منتجة، إلكترونيات).
