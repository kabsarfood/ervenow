# Gap Analysis — مسار المطاعم والمتاجر مقابل التصور المعتمد

**النوع:** تحليل فقط — لا تعديل كود ولا مسار جديد.  
**التاريخ:** 22 سبتمبر 2026  
**المصادر:** `register-store.html` · `apps/store/routes.js` · `apps/admin/routes.js` · `admin/modules/approvals.js` · `merchant-preview.js` · `store.html` · `shared/domain/orders/*` · `docs/ERVENOW_COMPLETE_PLATFORM_MAP.md`

---

## الخلاصة التنفيذية

جزء كبير من **التشغيل بعد الاعتماد** منفّذ فعلاً: بوابة تاجر واحدة، منتجات وأسعار وصور، صفحة عميل، سلة، طلبات، محفظة وسحب، تقييمات، وإشعارات.

ما يختلف عن التصور ليس «غياب المنصة»، بل **ترتيب الرحلة**:

1. المنتجات والرخصة ليست في طلب الانضمام.
2. موافقة الأدمن = ظهور فوري للعملاء، بلا خطوة «أكمل الصفحة ثم انشر».
3. الكاشير غير مبني (عنصر قائمة معطّل).
4. المطعم والمتجر **ليسا مسارين منفصلين** — نفس الجدول ونفس التسجيل ونفس البوابة، مع تمييز بالنوع (`type`) وصفحات تصفح منفصلة.

## حقيقة معمارية مهمة

| التصور | الواقع |
|---|---|
| مطعم مستقل + متجر مستقل | كيان واحد: صف في جدول `stores` |
| بوابة مطعم / بوابة متجر | بوابة واحدة: `/merchant-preview` لأدوار `store` · `merchant` · `restaurant` |
| تسجيل مطعم منفصل | `/register-store` مع اختيار نوع النشاط (مطعم / صيدلية / سوبرماركت / تجميل / ورود / ملابس) |
| صفحة مطعم للعميل | نفس `/store.html?id=` للمطعم والمتجر |
| قائمة مطاعم / متاجر | منفصلة: `/restaurants` و `/stores` |

كل ما يلي ينطبق على الاثنين ما لم يُذكر خلاف ذلك.

## أين يتقدّم الواقع على التصور

هذه ليست فجوات؛ قدرات موجودة زيادة:

- نطاق توصيل عند التسجيل.
- حساب بنكي / STC Pay اختياري عند الطلب.
- بيانات «من عبّأ الطلب».
- شعار وغلاف يمكن رفعهما مبكراً.
- عروض سعر (`offer_price`) وفئات منتجات التاجر.
- تقارير مبيعات داخل البوابة.
- طباعة حرارية للطلب (`order-board` / workflow).
- سلة موحّدة وcheckout للعميل.

## أين ينعكس ترتيب الرحلة

```
التصور:
OTP → اسم → موقع → منتجات+أسعار+صور → سجل → رخصة → مراجعة
→ قبول/رفض/استكمال
→ إشعار «أكمل الصفحة»
→ فئة+شعار+غلاف+وصف+منتجات+توفر → نشر
→ ظهور للعملاء

الواقع:
OTP في /login → اسم+نوع+فئة → موقع → نطاق توصيل → شعار/غلاف اختياري
→ سجل تجاري → دفع اختياري → pending
→ أدمن: قبول أو رفض (أو يعبّئ الصفحة بنفسه)
→ is_active=true فوراً → يظهر في /restaurants أو /stores
→ التاجر يدخل /merchant-preview ويكمل المنتجات لاحقاً
```

## تقييم الاكتمال التقريبي (حسب مرحلة التصور)

| كتلة التصور | تقدير التغطية | ملاحظة |
|---|---|---|
| 1 طلب الانضمام | ~55% | OTP، اسم، موقع، سجل. بلا منتجات أولية ولا رخصة |
| 2 مراجعة الأدمن | ~40% | قبول/رفض يعملان. بلا مراجعة وثائق/منتجات ولا طلب استكمال |
| 3 بعد الموافقة | ~70% | إشعار وبوابة موجودان. النص و«أكمل الصفحة» ناقصان |
| 4 استكمال ونشر | ~60% | القدرات موجودة. معالج النشر غير موجود؛ الظهور فوري |
| 5 صفحة العميل | ~90% | المسار الأقوى قرباً من التصور |
| 6 بوابة التاجر | ~80% | كل الأقسام عدا POS؛ ازدواج لوحات كلاسيكية |
| 7 دورة الطلب | ~75% | قبول→تجهيز→جاهز عند التاجر. الاستلام/الطريق/التسليم عند المندوب |
| 8 الكاشير | ~5% | placeholder + وحدة `disabled` |

## الفجوات ذات الأولوية (تحليل فقط — بلا تنفيذ)

1. **كتالوج أولي داخل طلب الانضمام** — أكبر فرق في مرحلة 1.
2. **الرخصة** — غير موجودة في النموذج والـAPI والتخزين.
3. **شاشة مراجعة أدمن حقيقية** — عارض سجل + موقع + (لاحقاً رخصة ومنتجات) بدل `alert` JSON.
4. **طلب استكمال بيانات** — حالة ثالثة غير القبول/الرفض.
5. **فصل الاعتماد عن النشر** — موافقة الحساب ≠ ظهور الكتالوج للعملاء.
6. **إشعار «أكمل صفحة المطعم/المتجر»** — تغيير رسالة لا محرك جديد.
7. **POS فرع** — غير مبني؛ الوحدة متعمّد إيقافها.
8. **توحيد منزل التاجر** — التشغيل الحقيقي مبعثر على preview + store-dashboard + order-board.

ساعات العمل مؤجّلة في التصور وفي الكود — ليست فجوة عاجلة إلا عند اعتماد «لاحقاً» كمرحلة تالية.

## ما يمكن اعتباره منفّذاً بالفعل
